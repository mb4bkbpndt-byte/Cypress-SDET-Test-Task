# Обнаруженные дефекты

Здесь я собрал расхождения, которые получил при проверке неизменённого
`payment_sandbox.py` через HTTP. Коды ответов и `payment_id` взяты из
фактических прогонов. Для краткости часть ключей и ref обозначил метками;
в BUG-009 оставил полный ключ и ref. Метка `known_defect` не скрывает падение
теста: она нужна мне только для запуска выбранной группы.

| Дефект | Критичность | Связанные сценарии |
|---|---|---|
| BUG-001: изменённое тело не вызывает конфликт | Высокая | 3, включая конкурентный |
| BUG-002: принимаются нулевая и отрицательная суммы | Высокая | 2 |
| BUG-003: boolean принимается как сумма | Высокая | 2 |
| BUG-004: повтор после `fail-after-create` создаёт дубль | Высокая | 4 |
| BUG-005: нет валидации `corridor` | Высокая | 7 |
| BUG-006: объект или массив в `currency` обрывает соединение | Высокая | 2 |
| BUG-007: нет валидации `beneficiary_ref` | Высокая | 7 |
| BUG-008: JSON неправильного верхнего типа обрывает соединение | Высокая | 4 |
| BUG-009: гонка при первичном создании с одним ключом | Высокая | 2, падение нестабильно |

В первом контрольном запуске у меня было `31 passed / 30 failed`. После
усиления конкурентной проверки один полный прогон дал `30 passed / 31 failed`.
Я не складываю числа из таблицы: один сценарий может относиться к двум
дефектам, а гонка BUG-009 проявляется не при каждом запуске. Кроме того, не
все падения доказывают нарушение явно сформулированного контракта. Для
положительной суммы и формата `corridor`/`beneficiary_ref` я использую
допущения, отмеченные `assumption`. PDF не перечисляет поддерживаемые валюты,
поэтому отклонение `EUR` я также проверяю как допущение, а не как отдельный
дефект.

## BUG-001. Изменённое тело с тем же ключом возвращает `200` вместо `409`

**Критичность:** высокая. **Endpoint:** `POST /v1/payments`.

**Как я воспроизвёл.** Я создал платёж с новым ключом, затем повторил запрос с
тем же ключом и другой суммой. Получил исходный платёж по ID и по
`beneficiary_ref`, сверил `amount`, `currency`, `corridor` и
`beneficiary_ref`. Отдельно повторил сценарий с другим `beneficiary_ref`.

**Что я ожидал.** Изменённая инструкция должна получить `409`. Исходный
платёж должен остаться единственным и сохранить все поля. Повтор исходного
тела должен вернуть `200` и тот же ID.

**Что я получил.**

```text
Idempotency-Key: <ключ A>
beneficiary_ref: <ref A>
первый запрос, amount=100000 -> 201, payment_id=P-e391ca968389
изменённый запрос, amount=100001 -> 200, payment_id=P-e391ca968389
повтор исходного тела -> 200, payment_id=P-e391ca968389
debug -> count=1, payment_ids=[P-e391ca968389]

Idempotency-Key: <ключ B>
исходный ref: <ref B>
изменённый ref: <ref C>
первый запрос -> 201, payment_id=P-1284212a9871
запрос с изменённым ref -> 200, payment_id=P-1284212a9871
debug исходного ref -> count=1, payment_ids=[P-1284212a9871]
debug изменённого ref -> count=0, payment_ids=[]
```

В конкурентном сценарии я сопоставил каждый ответ с отправленным ему телом.
Зафиксировал `200`, в котором была сохранённая инструкция другого варианта.
После одновременной отправки я последовательно повторяю оба тела: сохранённое
должно вернуть исходный ID, другое — `409`, без изменения записей.

**Риск.** Запрос с другой платёжной инструкцией может выглядеть успешно
обработанным, хотя сервис сохранил первоначальную. В этом дефекте второго
платежа в последовательном сценарии нет; отсутствие конфликта само по себе
создаёт ложное подтверждение.

**Тесты:** `test_reuse_key_with_changed_amount_returns_409_without_side_effect`,
`test_reuse_key_with_changed_beneficiary_returns_409_without_side_effect`,
`test_concurrent_different_bodies_with_one_key_create_one_payment`.

## BUG-002. Принимаются нулевая и отрицательная суммы

**Критичность:** высокая. **Endpoint:** `POST /v1/payments`.

**Как я воспроизвёл.** Я отправил две инструкции с новыми ключами: сначала
`amount=0`, затем `amount=-1`. После каждого запроса проверил платежи по
`beneficiary_ref`.

**Что я ожидал.** `422` и ни одного созданного платежа. Это ожидание зависит
от моего допущения, что сумма должна быть строго больше нуля: точная граница
суммы в задании не указана. Поведение ключа после `422` в этот тест не входит.

**Что я получил.**

```text
amount=0; key=<ключ A>
ref=<ref A>
ответ -> 201, payment_id=P-bf0206bf7a42
debug -> count=1, payment_ids=[P-bf0206bf7a42]

amount=-1; key=<ключ B>
ref=<ref B>
ответ -> 201, payment_id=P-1e0c563e1d17
debug -> count=1, payment_ids=[P-1e0c563e1d17]
```

В дополнительной диагностике я исправил сумму и повторил запрос с тем же
ключом: оба раза получил `200` и первоначальную некорректную сумму. Этот
повтор не использую как обязательное ожидание негативного теста.

**Риск.** При принятом правиле положительной суммы сервис сохраняет
некорректную операцию и связывает её с ключом.

**Тесты:** `test_invalid_amount_returns_422_without_payment[zero]`,
`test_invalid_amount_returns_422_without_payment[negative]`.

## BUG-003. Boolean принимается в `amount` как число

**Критичность:** высокая. **Endpoint:** `POST /v1/payments`.

**Как я воспроизвёл.** Я отправил запрос с `amount=true`, затем отдельный
запрос с `amount=false`. В обоих случаях проверил сохранённый платёж.

**Что я ожидал.** `422` и отсутствие платежа: JSON boolean не является
денежной суммой.

**Что я получил.**

```text
amount=true; key=<ключ A>
ref=<ref A>
ответ -> 201, payment_id=P-2aefe2d320b1
debug -> count=1, сохранён amount=true

amount=false; key=<ключ B>
ref=<ref B>
ответ -> 201, payment_id=P-546a0a64f54b
debug -> count=1, сохранён amount=false
```

**Риск.** Сервис принимает и сохраняет значение другого типа вместо суммы.

**Тесты:** `test_invalid_amount_returns_422_without_payment[boolean-true]`,
`test_invalid_amount_returns_422_without_payment[boolean-false]`.

## BUG-004. Повтор после `fail-after-create` создаёт второй платёж

**Критичность:** высокая. **Endpoint:** `POST /v1/payments`.

**Как я воспроизвёл.** Я отправил запрос с новым ключом и заголовком
`X-Simulate: fail-after-create`. После `500` проверил платежи по
`beneficiary_ref`, сохранил ID уже созданной записи и повторил исходное тело с
тем же ключом без `X-Simulate`.

**Что я ожидал.** После `500` должна существовать одна операция. Повтор
должен вернуть её ID без создания второй; итоговый `count` должен остаться 1.

**Что я получил.**

```text
key=<новый ключ>
ref=<новый ref>
запрос с fail-after-create -> 500, {"error":"upstream timeout"}
debug до повтора -> count=1, payment_ids=[P-cc384f74436a]
первый повтор -> 201, payment_id=P-12bc60af3f85
второй повтор -> 200, payment_id=P-12bc60af3f85
debug после повторов -> count=2,
payment_ids=[P-cc384f74436a, P-12bc60af3f85]
```

Я проверил также повтор с изменёнными `amount` и `beneficiary_ref`: вместо
конфликта получил `201` и вторую запись. При 20 конкурентных повторах после
`500` ответы ссылались на новый ID, а общее число записей осталось равным 2.

**Риск.** Я подтвердил две записи с разными `payment_id`. В реальной
платёжной системе это создаёт риск повторной финансовой обработки, но сама
песочница не моделирует списание денег. Утверждать о двойном списании по этому
тесту нельзя. Гонка без `fail-after-create` описана отдельно в BUG-009.

**Тесты:** четыре сценария в `tests/test_failure_recovery.py`.

## BUG-005. Нет валидации `corridor`

**Критичность:** высокая. **Endpoint:** `POST /v1/payments`.

**Как я воспроизвёл.** Я передал в `corridor` значения неправильного типа и
пустые строки. Для каждого случая проверил платежи по валидному
`beneficiary_ref`.

**Что я ожидал.** При моём допущении, что `corridor` должен быть непустой
строкой, — `422` и отсутствие платежа. Контракт требует наличие поля и
описывает `422` для невалидного тела, но отдельно не задаёт тип и непустоту
`corridor`. Поэтому я пометил эти случаи `assumption`.

**Что я получил.**

```text
key=<новый ключ>
ref=<новый ref>
corridor=null -> 201, payment_id=P-300a8b4a20eb
debug -> count=1, payment_ids=[P-300a8b4a20eb]
исправленный запрос с тем же ключом -> 200, payment_id=P-300a8b4a20eb,
в ответе по-прежнему corridor=null
```

Я получил такое же принятие для числа, boolean, объекта, массива, пустой
строки и строки из пробелов. Повтор с исправленным телом — дополнительное
наблюдение, а не часть обязательного ожидания негативного теста.

**Риск.** Если бизнес-правило требует непустую строку, сервис сохраняет
некорректный маршрут платежа.

**Тесты:** семь параметров `corridor-*` в
`test_invalid_string_field_returns_422_without_observable_payment`.

## BUG-006. Объект или массив в `currency` обрывает соединение

**Критичность:** высокая. **Endpoint:** `POST /v1/payments`.

**Как я воспроизвёл.** Я отправил JSON-объект вместо значения `currency`,
затем повторил проверку с массивом. После каждого запроса проверил
диагностический список по валидному ref.

**Что я ожидал.** Для невалидного тела — HTTP `422` без создания платежа и
без разрыва соединения.

**Что я получил.**

```text
key=<новый ключ>
ref=<новый ref>
currency={"value":"RUB"} -> HTTP-ответ отсутствует,
ConnectionError: RemoteDisconnected('Remote end closed connection without response')
debug -> count=0, payment_ids=[]
исправленный запрос с тем же ключом -> 201, payment_id=P-e525722066f5
```

Для массива я получил такой же разрыв. Ошибочный запрос не создал платёж,
однако вместо контролируемого HTTP-ответа соединение было закрыто.

**Риск.** Разрыв соединения оставляет результат запроса неопределённым для
отправляющей системы и осложняет безопасный повтор.

**Тесты:** параметры `currency-object` и `currency-array` в
`test_invalid_string_field_returns_422_without_observable_payment`.

## BUG-007. Нет валидации `beneficiary_ref`

**Критичность:** высокая. **Endpoint:** `POST /v1/payments`.

**Как я воспроизвёл.** Я отправил `beneficiary_ref=null` с новым ключом и
получил платёж по ID из ответа. Также проверил число, boolean, объект,
массив, пустую строку и строку из пробелов.

**Что я ожидал.** При моём допущении о непустой строке — `422` без платежа.
Контракт требует наличие поля, но отдельно не задаёт его формат. Поэтому
ожидание для перечисленных значений я пометил `assumption`.

**Что я получил.**

```text
key=<новый ключ>
beneficiary_ref=null -> 201, payment_id=P-16171c536088
GET /v1/payments/P-16171c536088 -> 200
исправленный ref=<новый ref>
исправленный запрос с тем же ключом -> 200, payment_id=P-16171c536088,
в ответе по-прежнему beneficiary_ref=null
debug исправленного ref -> count=0, payment_ids=[]
```

Остальные перечисленные значения сервис также принял. Для `null`, числа,
boolean, объекта, массива и пустой строки я не могу найти исходную запись
через `/debug/payments`: endpoint требует непустой строковый ref. В этом
примере создание подтверждают `201` и `GET` по ID. При гипотетическом `422`
без ID доказать отсутствие скрытой записи через выданный API не получилось бы.

**Риск.** При принятом правиле формата сохраняется операция без корректного
идентификатора получателя.

**Тесты:** семь параметров `beneficiary-*` в
`test_invalid_string_field_returns_422_without_observable_payment`.

## BUG-008. JSON неправильного верхнего типа обрывает соединение

**Критичность:** высокая. **Endpoint:** `POST /v1/payments`.

**Как я воспроизвёл.** Я отправил JSON `null`, затем проверил число, `true`
и `false` как документы верхнего уровня.

**Что я ожидал.** HTTP `422` без создания платежа и без разрыва соединения.

**Что я получил.**

```text
key=<новый ключ>
raw body: null
HTTP-ответ отсутствует,
ConnectionError: RemoteDisconnected('Remote end closed connection without response')
исправленный запрос с тем же ключом -> 201, payment_id=P-3546d0b96bac
ref=<новый ref>
debug -> count=1, payment_ids=[P-3546d0b96bac]
```

Для числа, `true` и `false` я получил такой же разрыв. Повреждённый JSON,
пустое тело, массив и строка вернули `422`, поэтому к этому дефекту их не
отношу. Повтор исправленного тела после ошибки использовал для диагностики,
но не закреплял как часть базового ожидания после `422`.

**Риск.** Вместо предусмотренной ошибки валидации возникает неопределённый
сетевой результат.

**Тесты:** параметры `json-null`, `json-number`, `json-true`, `json-false` в
`test_invalid_json_document_returns_422_without_observable_payment`.

## BUG-009. Гонка при первичном создании с одним ключом

**Критичность:** высокая. **Endpoint:** `POST /v1/payments`.

**Как я воспроизвёл.** Я запустил неизменённый сервис, подготовил новый ключ
и ref и одновременно отправил 20 одинаковых запросов без `X-Simulate`. В
тесте общий барьер запускает отправку из 20 потоков. После ответов я
проверил `/debug/payments` по ref. При отсутствии гонки повторил раунд с
новыми данными.

**Что я ожидал.** Один платёж, один ответ `201`, для повторов с тем же телом —
`200` с одним ID, в диагностическом списке `count=1`. Для разных тел с одним
ключом я дополнительно ожидаю отсутствие ложного успешного ответа на другую
инструкцию; точное сочетание кодов во время одновременной отправки не
фиксирую.

**Что я получил.** Пример из повторного прогона: падение на четвёртом запуске,
во втором раунде.

```text
Idempotency-Key: concurrent-2-64d2396e009b4f13bd22174ab672d8f0
beneficiary_ref: concurrent-2-7ac149b51dfd43489ac38eee12108d97
тело: corridor=RUB/THB, amount=100000, currency=RUB
ответы 20 запросов: 201 x 2, 200 x 18
payment_id в ответах: P-f40126a47db9 и P-01c500a47c6b
GET /debug/payments?beneficiary_ref=concurrent-2-7ac149b51dfd43489ac38eee12108d97
-> 200, count=2,
payments=[
  {payment_id: P-f40126a47db9, idempotency_key: concurrent-2-64d2396e009b4f13bd22174ab672d8f0},
  {payment_id: P-01c500a47c6b, idempotency_key: concurrent-2-64d2396e009b4f13bd22174ab672d8f0}
]
```

Я зафиксировал нестабильность дефекта. В серии из 20 запусков сценарий с
одинаковыми телами упал 2 раза, с разными — 10 раз; в каждом запуске было
по три раунда. Эти числа не оценивают вероятность ошибки. Для разных тел я
также увидел `200` с данными варианта, отличного от отправленного. Поэтому
проверяю не только число записей, но и соответствие каждого успешного ответа
его запросу, затем повторяю оба варианта последовательно и сверяю итоговое
состояние по обоим ref.

**Риск.** Я подтвердил две записи с одним ключом без смоделированного сбоя.
Это создаёт риск повторной финансовой обработки в реальной системе, но
песочница не моделирует списание денег. Ложный `200` дополнительно может
скрыть, какая инструкция фактически сохранена. BUG-004 — другой дефект: там
дубль появляется после `500` от `fail-after-create`.

**Тесты:** `test_concurrent_replay_creates_exactly_one_payment`,
`test_concurrent_different_bodies_with_one_key_create_one_payment`.
