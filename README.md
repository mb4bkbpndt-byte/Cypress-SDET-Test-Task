# Cypress-SDET Test Task

Здесь собраны три части моей проверки платежей: автотесты HTTP API, сверка
наших записей с выпиской партнёра и один браузерный сценарий оплаты.
`payment_sandbox.py` оставлен без изменений. Браузерная форма — отдельный
демонстрационный интерфейс; она не отправляет платежи в API-песочницу.

## Запуск

Проверял проект на Python 3.14.4. Из корня проекта создаю окружение и ставлю
зависимости:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m playwright install chromium --only-shell
```

Для API-тестов сначала запускаю сервис и оставляю его работающим:

```bash
python payment_sandbox.py
```

В другом терминале из корня проекта запускаю проверки. Первый вариант
исключает уже описанные дефекты, второй выполняет **все** API-тесты и поэтому
на текущем сервисе ожидаемо показывает падения:

```bash
python -m pytest tests -q -m "not known_defect"
python -m pytest tests -q
```

Адрес сервиса по умолчанию — `http://127.0.0.1:8080`; при необходимости меняю
его через `PAYMENTS_BASE_URL`, таймаут — через `PAYMENTS_REQUEST_TIMEOUT`.
Если API-тесты дают ошибку соединения, сначала проверяю, запущен ли сервис
и свободен ли порт `8080`.

Сверку выписки и браузерный сценарий запускаю независимо от API:

```bash
python reconciliation/run_reconciliation.py
python -m pytest browser/tests -q
```

Если браузерный тест сообщает об отсутствии Chromium, повторяю команду
`python -m playwright install chromium --only-shell` в активном окружении.

## Что лежит в проекте

**API.** В `tests/` проверяю создание и получение платежа, идемпотентность,
конфликт при изменении инструкции, валидацию и восстановление после
`fail-after-create`. Для сценариев создания смотрю не только на HTTP-код, но
и на фактическое число платежей через диагностический endpoint. Отдельно
проверяю конкурентные запросы; гонка при первичном создании проявляется не в
каждом прогоне. Детальные шаги, ответы и оговорки к требованиям собраны в
[`BUG_REPORTS.md`](BUG_REPORTS.md). Известные дефекты помечены
`known_defect`, но не скрыты через `xfail`. Часть ожиданий, например к
границе суммы и формату отдельных полей, помечена `assumption`: они не
равнозначны явно записанному контракту.

**Реконсиляция.** Исходные CSV оставил в `reconciliation/data/`. Скрипт
[`run_reconciliation.py`](reconciliation/run_reconciliation.py) загружает обе
таблицы во временную SQLite-базу и выполняет семь именованных запросов из
[`reconcile.sql`](reconciliation/reconcile.sql). Именно там находятся SQL для
записей только у нас или только у партнёра, расхождений суммы и статуса,
дублей и контрольных проверок валюты. Результаты разбора записал в
[`FINDINGS.md`](reconciliation/FINDINGS.md): пять непустых категорий, без
расхождений валют и дублей `ref` в нашем файле. Сопоставляю по `ref`;
сумму и статус сравниваю только там, где в каждом источнике ровно одна запись
с этим ref. Иначе соединение по дублю исказило бы результат. Без времени
среза и правил обновления статусов это расхождения источников, а не
доказанные причины инцидентов.

**Браузер.** Тест в [`browser/tests/`](browser/tests/) проходит локальную
форму: ввод данных, проверка страницы подтверждения и итогового статуса.
Страницы лежат в `browser/demo/`; тест сам поднимает для них локальный сервер
на свободном порту. Page Object здесь не добавлял: сценарий один, страницы
маленькие, а локаторы по ролям, подписям и ID читаются прямо в тесте. Отдельный
класс сейчас лишь спрятал бы короткий путь за дополнительным слоем. Если
появятся новые сценарии или начнут повторяться действия и локаторы, вынесу
их в объекты страниц. Этот тест проверяет только поведение демонстрационной
формы: реального платёжного шлюза и списания здесь нет.

При большем времени расширил бы конкурентные прогоны API, уточнил правила
периода и статусов для сверки, а для полноценного UI добавил бы негативные
пути и связал подтверждение с настоящим API. Для регулярных прогонов пригодился
бы отчёт Allure с запросом, ответом и состоянием платежей при падении.
